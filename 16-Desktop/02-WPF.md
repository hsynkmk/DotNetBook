# WPF

## The mature XAML framework

**WPF** (Windows Presentation Foundation) is the most full-featured Windows UI framework: XAML markup, a powerful **data binding** system, **MVVM** ([Ch15 §06](../15-MAUI/06-MVVM.md)), and a vector-based, fully templatable rendering engine. Though dating to 2006, it runs on modern .NET (.NET 10) and remains the pragmatic choice for serious Windows line-of-business apps thanks to its maturity, deep capabilities (styles, templates, triggers, animations), and enormous ecosystem.

```xml
<Window x:Class="MyApp.MainWindow"
        xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
        Title="Demo" Height="300" Width="400">
    <StackPanel Margin="16">
        <TextBlock Text="{Binding Greeting}" FontSize="20" />
        <Button Content="Click" Command="{Binding ClickCommand}" />
    </StackPanel>
</Window>
```

---

## XAML and the visual tree

WPF UIs are XAML trees rooted in a `Window` (or `Page`/`UserControl`). The concepts mirror MAUI XAML ([Ch15 §02](../15-MAUI/02-XAML.md)) — elements are objects, attributes are properties, `{Binding}` and `{StaticResource}` markup extensions, attached properties (`Grid.Row`), resources/styles — but the controls and some dialects differ (WPF's namespace is the 2006 presentation schema; layout panels are `Grid`, `StackPanel`, `DockPanel`, `WrapPanel`, `Canvas`). WPF distinguishes the **logical tree** (the declared element hierarchy) from the **visual tree** (every visual element including those generated by control templates) — relevant when styling/templating deeply.

## Dependency properties — WPF's property system

WPF's defining feature is the **dependency property** system. Unlike a plain CLR property, a dependency property:

- Supports **data binding** as a target,
- Participates in **styling, animation, and property-value inheritance** (a value can flow down the tree),
- Has a **value-precedence** system (local value > style trigger > style > inherited > default),
- Stores values efficiently (not one field per property per instance).

```csharp
public class MyControl : Control {
    public static readonly DependencyProperty CountProperty =
        DependencyProperty.Register(nameof(Count), typeof(int), typeof(MyControl),
            new PropertyMetadata(0, OnCountChanged));

    public int Count {
        get => (int)GetValue(CountProperty);
        set => SetValue(CountProperty, value);
    }
    static void OnCountChanged(DependencyObject d, DependencyPropertyChangedEventArgs e) { /* react */ }
}
```

You define dependency properties when building **custom controls** that need to be bindable/animatable/styleable targets. For ordinary view-model properties you use plain properties with `INotifyPropertyChanged` ([Ch15 §06](../15-MAUI/06-MVVM.md)) — dependency properties are for the *control* side, not the view-model side.

## Data binding — the powerhouse

WPF's binding engine is exceptionally rich:

```xml
<TextBox Text="{Binding Name, Mode=TwoWay, UpdateSourceTrigger=PropertyChanged}" />
<TextBlock Text="{Binding Price, StringFormat='{}{0:C}'}" />
<ItemsControl ItemsSource="{Binding Items}" />
<TextBlock Text="{Binding SelectedItem.Name, ElementName=listBox}" />
```

- **Modes**: `OneWay`, `TwoWay`, `OneTime`, `OneWayToSource`; `UpdateSourceTrigger` controls when the source updates (e.g., per keystroke vs on focus loss).
- **Sources**: the `DataContext` (the WPF equivalent of MAUI's `BindingContext`), another element (`ElementName`), `RelativeSource` (self/ancestor), or a static resource.
- **Converters** (`IValueConverter`) transform values in the binding (e.g., bool → Visibility).
- **`ObservableCollection<T>`** + `INotifyPropertyChanged` make collections and properties update the UI ([Ch15 §06](../15-MAUI/06-MVVM.md)).

This binding depth is a major reason WPF endures for data-heavy business apps.

## Styles, templates, and triggers

WPF's theming/customization is best-in-class:

- **Styles** (`<Style TargetType="Button">`) set properties across controls (implicit if keyless, like MAUI).
- **Control templates** (`ControlTemplate`) **completely redefine a control's visual structure** while keeping its behavior — e.g., make a `Button` look like anything, without losing click behavior. This is more powerful than most frameworks' styling.
- **Data templates** (`DataTemplate`) define how a *data object* is rendered (used by item controls).
- **Triggers** (`Trigger`, `DataTrigger`, `EventTrigger`) change properties in response to property/data/event conditions declaratively (e.g., turn a row red when `IsOverdue` is true) — without code-behind.

```xml
<Style TargetType="Button">
    <Setter Property="Background" Value="SteelBlue" />
    <Style.Triggers>
        <Trigger Property="IsMouseOver" Value="True">
            <Setter Property="Background" Value="DodgerBlue" />
        </Trigger>
    </Style.Triggers>
</Style>
```

## MVVM in WPF

MVVM is the standard WPF architecture, identical in concept to [Ch15 §06](../15-MAUI/06-MVVM.md): set a `Window`'s `DataContext` to a view-model, bind controls to its properties/commands, and use **CommunityToolkit.Mvvm** (`[ObservableProperty]`, `[RelayCommand]`, `ObservableObject`) to eliminate `INotifyPropertyChanged`/`ICommand` boilerplate. WPF predates the toolkit and historically used `RelayCommand`/`DelegateCommand` implementations from MVVM frameworks (Prism, MVVM Light) — but the toolkit's source-generated approach is now the modern default. Commands (`ICommand`) bind to buttons with `CanExecute` gating, exactly as elsewhere.

WPF supports DI via the Generic Host too — bootstrap a host, register view-models/services, and resolve the main window from the container ([Ch03](../03-HostingAndDI/README.md), [Ch15 §07](../15-MAUI/07-DependencyInjection.md)).

## Common gotchas

### Confusing dependency properties with view-model properties

Dependency properties are for **controls** (bindable/animatable targets); view-model properties are plain properties with `INotifyPropertyChanged`. Don't make view-model properties dependency properties — it's unnecessary and couples the VM to WPF.

### Logic in code-behind instead of MVVM

`Button_Click` handlers in code-behind couple UI to logic and hurt testability. Bind `Command`s to a view-model (MVVM) — [Ch15 §06](../15-MAUI/06-MVVM.md).

### Forgetting `UpdateSourceTrigger`

By default a `TextBox` updates its bound source on **focus loss**, not per keystroke. For live updates (validation as you type), set `UpdateSourceTrigger=PropertyChanged`.

### `List<T>` instead of `ObservableCollection<T>`

A plain list doesn't notify the UI of add/remove. Use `ObservableCollection<T>` for dynamic bound collections.

### Binding errors are silent

A typo'd binding path fails silently (logged to the Output window). Watch the debug Output for binding errors, or use a binding-error trace listener.

## Summary

- **WPF** is the mature, full-featured Windows XAML framework — **data binding**, **MVVM**, and a vector, fully **templatable** rendering engine — the pragmatic choice for serious Windows business apps (runs on modern .NET).
- Its defining feature is the **dependency property** system (binding/animation/styling targets, value-precedence, inheritance) — used when building **custom controls**, not for view-model properties (those use `INotifyPropertyChanged`).
- The **binding** engine is exceptionally rich (modes, `UpdateSourceTrigger`, `ElementName`/`RelativeSource`, converters); **styles/control templates/triggers** allow deep, code-free visual customization (a `ControlTemplate` can fully redefine a control's look while keeping behavior).
- **MVVM** is the standard architecture — set `DataContext`, bind to view-model properties/commands, use **CommunityToolkit.Mvvm** ([Ch15 §06](../15-MAUI/06-MVVM.md)) and Generic-Host DI; view-models are portable to WinUI 3/Avalonia.
