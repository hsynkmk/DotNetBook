# Chapter 16 — Desktop — Q & A

---

### Q1. What are the desktop UI options on .NET, and their niches?

**WPF** (mature XAML/MVVM workhorse — serious Windows business apps), **WinUI 3** (modern Fluent, Windows App SDK — new modern Windows apps), **WinForms** (designer/event model — fast internal tools/utilities), and **Avalonia** (OSS cross-platform XAML — Win/macOS/Linux desktop). All run on modern .NET.

---

### Q2. What do WPF, WinUI 3, and Avalonia share?

**XAML + data binding + MVVM.** The MVVM pattern, `INotifyPropertyChanged`, commands, and CommunityToolkit.Mvvm work across all three, so **view-models and logic are portable** — only the View (XAML dialect + controls) differs. WinForms is the event/designer exception.

---

### Q3. When would you choose WPF over WinUI 3?

For a serious/conservative Windows business app needing a **mature ecosystem**, vast third-party controls, and battle-tested stability, especially when you don't specifically need Fluent visuals. WinUI 3 is newer/less mature; WPF remains the pragmatic choice for many LOB apps.

---

### Q4. When would you choose WinUI 3?

For a **new** Windows app that should look **modern (Fluent)**, want the latest Windows 11 controls (`NavigationView`, mica/acrylic), Store/MSIX distribution, and align with Microsoft's strategic direction — accepting a newer, still-maturing framework.

---

### Q5. When is WinForms still the right call?

For **internal tools, utilities, prototypes, and data-entry/CRUD** apps where speed-to-build and stability beat visual polish — or maintaining existing WinForms apps. `DataGridView` + simple binding makes tabular apps trivial. Not for modern-looking or cross-platform apps.

---

### Q6. What is a dependency property in WPF and when do you define one?

WPF's special property type that supports binding (as a target), styling, animation, value-precedence, and property-value inheritance, stored efficiently. You define them when building **custom controls** that need bindable/animatable/styleable properties — **not** for view-model properties (those use `INotifyPropertyChanged`).

---

### Q7. What's the difference between the logical and visual tree in WPF?

The **logical tree** is the declared element hierarchy; the **visual tree** is every visual element including those generated by control templates. Relevant when styling/templating deeply or walking the tree.

---

### Q8. What can a WPF `ControlTemplate` do?

**Completely redefine a control's visual structure** while preserving its behavior — e.g., make a `Button` look like anything without losing click behavior. Combined with styles, data templates, and triggers, it gives WPF best-in-class, code-free visual customization.

---

### Q9. What is `{x:Bind}` and how does it differ from `{Binding}`?

`{x:Bind}` (WinUI 3) is a **compiled** binding: resolved against the page code-behind, generated at compile time, **type-checked** (errors at build), and faster than reflection-based `{Binding}`. It defaults to `OneTime` (set `Mode=OneWay`/`TwoWay` for updates). `{Binding}` is DataContext-based and reflection-driven.

---

### Q10. How is WinUI 3 different from old UWP?

WinUI 3 (Windows App SDK) **decouples** the modern UI stack from UWP and the OS: you build a **standard .NET desktop app** with full Win32/BCL access (not UWP-sandboxed), using the modern Fluent controls, and updates ship via the App SDK rather than Windows releases.

---

### Q11. What's the WinForms programming model?

A **visual designer** (drag controls onto a form, generated `*.Designer.cs`) plus **event handlers** in code-behind (`Click`, `TextChanged`). Immediate and productive, but logic tends to live in code-behind. Supports simple data binding (`BindingSource`/`BindingList<T>`) and modern .NET adds Generic Host/DI.

---

### Q12. How does Avalonia differ from WPF and MAUI?

It's **WPF-like XAML/MVVM** but **cross-platform** (Win/macOS/Linux + more). Unlike MAUI (native controls per platform), Avalonia **draws its own controls** (Skia) for a **consistent look across all OSes**. Open-source, with CSS-like styling selectors and compiled bindings.

---

### Q13. Native vs self-rendered controls — Avalonia vs MAUI?

MAUI maps cross-platform controls to **native** widgets per platform (native look/feel). Avalonia **renders its own** controls via Skia (identical look everywhere). Native = platform-idiomatic; self-rendered = cross-platform consistency.

---

### Q14. What's the single most important desktop performance rule?

**Never block the UI thread.** Desktop frameworks are single-UI-threaded; synchronous I/O or CPU work freezes the app. Use `async`/`await` (I/O) and `Task.Run` (CPU), and marshal cross-thread UI updates via the dispatcher (`Dispatcher.Invoke`/`Control.Invoke`).

---

### Q15. How do you update a control from a background thread?

Marshal back to the UI thread: `Dispatcher.Invoke`/`BeginInvoke` (WPF/WinUI/Avalonia) or `Control.Invoke`/`BeginInvoke` (WinForms). Or simply `await`, which resumes on the UI synchronization context automatically. Touching a control directly from a background thread throws.

---

### Q16. What is UI virtualization and why does it matter?

Rendering only the items currently visible (+ buffer), recycling containers as you scroll — so a list of thousands isn't fully realized. It's the biggest win for data-heavy apps. WPF uses `VirtualizingStackPanel` (enable recycling); don't disable it by giving the list infinite height (e.g., in a ScrollViewer).

---

### Q17. What does `Freeze()` do in WPF?

Marks a `Freezable` (brush, pen, geometry) as immutable so WPF can skip change-tracking and share it (even across threads) — a cheap performance win for resources that won't change.

---

### Q18. What's a common desktop memory leak?

**Event-handler retention**: a short-lived view subscribing to a long-lived object's event without unsubscribing keeps the view alive. Fix by unsubscribing or using weak events (WPF's `WeakEventManager`).

---

### Q19. Self-contained vs framework-dependent deployment?

**Framework-dependent** needs .NET installed on the target (small). **Self-contained** bundles the runtime (larger, frictionless on machines without .NET; `PublishSingleFile` makes one exe). Most consumer desktop apps go self-contained to avoid "install .NET first."

---

### Q20. Compare MSIX, ClickOnce, and Store deployment.

**MSIX**: modern Windows package — clean install/uninstall, auto-update, app identity, **signing required** (WinUI 3/Store apps). **ClickOnce**: low-ceremony auto-updating install for internal WPF/WinForms tools (per-user, no admin). **Store** (MSIX): consumer discoverability + trusted install/updates. Match to audience.

---

### Q21. Can you use Native AOT for a WPF/WinUI app?

Generally **no** — XAML UI frameworks rely on reflection/dynamic features AOT disallows. Trimming is also **risky** (can remove members used by XAML loading/binding). Use **ReadyToRun (R2R)** for safe startup gains instead; AOT suits console/server apps.

---

### Q22. Does MVVM lock you into one framework?

No. Because WPF/WinUI/Avalonia share XAML + binding + MVVM, **view-models and services are portable** across them — only the View layer differs. Architecting with MVVM (testable VMs, DI, CommunityToolkit.Mvvm) keeps the framework choice from being a deep lock-in.

---

### Q23. Why is signing important even for xcopy deployment?

Unsigned executables trigger **SmartScreen** warnings and erode user trust. Code-signing establishes integrity/trust; it's **mandatory** for MSIX and recommended for all distribution methods.
