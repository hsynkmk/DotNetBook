# I/O — Files, Streams, Pipelines

## The BCL I/O stack

`System.IO` is how your program crosses the boundary to disk, network, and memory. The model is layered: pure path strings (`Path`), filesystem operations (`File`/`Directory`), the byte-stream abstraction (`Stream`), text adapters (`StreamReader`/`Writer`), and the high-performance `System.IO.Pipelines`.

> CSharpBook Chapter 13 covers this in depth from the language angle (the `Stream.Read` contract, `Path.Combine`, atomic writes, `StreamReader` `leaveOpen`, pipelines). This file is the **BCL map + platform-specific details** (cross-platform path/filesystem behavior, async file I/O, `RandomAccess`, memory-mapped files) and points you to CSharpBook for the mechanics.

---

## The layers

```
Path            — pure string manipulation of paths (no disk access)
File/Directory  — filesystem operations (read/write/copy/enumerate)
FileInfo/DirectoryInfo — cached metadata for repeated queries
Stream          — the universal byte-sequence abstraction
  ├─ FileStream, MemoryStream, NetworkStream, GZipStream, CryptoStream...
StreamReader/Writer — char/text over a byte Stream (handles encoding)
System.IO.Pipelines — high-perf, low-alloc streaming parse
RandomAccess    — offset-based file I/O without a Stream position
MemoryMappedFile — map a file into memory for large/shared access
```

## Files & directories (the essentials)

```csharp
// Whole-file (convenient; loads into memory) — prefer async in servers
string text = await File.ReadAllTextAsync(path, ct);
await File.WriteAllTextAsync(path, json, ct);
byte[] bytes = await File.ReadAllBytesAsync(path, ct);

// Streaming large files lazily (constant memory)
await foreach (var line in File.ReadLinesAsync(path, ct))   // .NET 7+
    Process(line);

// Directory enumeration — prefer Enumerate* (lazy) over Get* (eager array)
foreach (var f in Directory.EnumerateFiles(root, "*.log", SearchOption.AllDirectories)) { }

Directory.CreateDirectory(path);     // idempotent — creates intermediates, no error if exists
File.Move(src, dst, overwrite: true);
```

Use **lazy** APIs (`ReadLinesAsync`, `EnumerateFiles`) for large inputs and **async** in server code to avoid blocking thread-pool threads ([Ch01 §08](../01-Runtime/08-Threading.md)). Full guidance — including the **atomic write** (temp + rename) pattern and path-traversal safety — is in CSharpBook Ch13 §01.

## Cross-platform path & filesystem behavior

Since modern .NET runs on Windows, Linux, and macOS, paths and filesystem semantics differ — `Path` abstracts most of it, but you must respect the differences:

```csharp
Path.Combine("logs", "app.log");      // "logs\app.log" (Windows) or "logs/app.log" (Unix)
Path.DirectorySeparatorChar;           // '\' on Windows, '/' on Unix
Path.GetTempPath();                    // platform temp dir
Path.GetFullPath(relative);            // resolves against cwd, normalizes
```

Cross-platform traps:
- **Separators** — always use `Path.Combine`, never hardcode `\` or `/` (CSharpBook Ch13 §01).
- **Case sensitivity** — Linux filesystems are **case-sensitive** (`File.txt` ≠ `file.txt`); Windows/macOS default case-insensitive. Don't assume.
- **Reserved names / chars** — Windows forbids `CON`, `PRN`, `:`, `*`, etc.; Unix is more permissive. Validate filenames if user-supplied.
- **Line endings** — `\r\n` (Windows) vs `\n` (Unix); use `Environment.NewLine`, or set `StreamWriter.NewLine` explicitly for a fixed format.
- **Permissions** — Unix file modes vs Windows ACLs differ; `File.SetUnixFileMode` (.NET 7+) handles Unix perms.

## Streams (the byte abstraction)

Everything I/O implements `Stream` — files, sockets, memory, compression, crypto — so they **compose**:

```csharp
// Read an encrypted, gzipped file as text — stream composition (decorator pattern)
await using var file = File.OpenRead("data.gz.enc");
await using var decrypt = new CryptoStream(file, decryptor, CryptoStreamMode.Read);
await using var gunzip  = new GZipStream(decrypt, CompressionMode.Decompress);
using var reader = new StreamReader(gunzip, Encoding.UTF8);
string content = await reader.ReadToEndAsync(ct);
```

The **cardinal `Stream.Read` rule**: `Read` may return **fewer bytes than requested** (0 = end of stream) — you must loop, or use `ReadExactly`/`CopyToAsync`. This is the #1 stream bug; see CSharpBook Ch13 §02 for the full contract, `leaveOpen`, flushing, and `MemoryStream` pitfalls.

Prefer the **`Span`/`Memory` overloads** and `CopyToAsync` over manual `byte[]` loops:

```csharp
await source.CopyToAsync(destination, bufferSize: 81920, ct);   // handles the loop for you
int n = await stream.ReadAsync(buffer.AsMemory(0, count), ct);   // Memory overload
```

## `FileStream` and true async file I/O

```csharp
await using var fs = new FileStream(
    path, FileMode.Open, FileAccess.Read, FileShare.Read,
    bufferSize: 4096, useAsync: true);                  // enable OS async I/O
```

`useAsync: true` (or the async `File.*` helpers) enables genuine asynchronous file I/O where the OS supports it (overlapped I/O on Windows, io_uring/threadpool offload on Linux). For servers, async file I/O frees the thread during the disk wait. `FileShare` controls concurrent access (the cause of "file in use" errors when set to `None`). Details: CSharpBook Ch13 §02.

## `RandomAccess` — offset I/O without a Stream (.NET 6+)

For reading/writing at specific offsets concurrently (databases, parallel readers) without a shared `Stream.Position`:

```csharp
using SafeFileHandle handle = File.OpenHandle(path, FileMode.Open, FileAccess.Read);
long length = RandomAccess.GetLength(handle);
byte[] buf = new byte[4096];
long read = await RandomAccess.ReadAsync(handle, buf, fileOffset: 8192, ct);
```

`RandomAccess` is **thread-safe** (no position to contend on), so multiple threads can read different offsets of the same file simultaneously — ideal for page-oriented file formats and databases.

## Memory-mapped files

For very large files or shared-memory IPC, map a file into the process address space and access it like memory:

```csharp
using System.IO.MemoryMappedFiles;
using var mmf = MemoryMappedFile.CreateFromFile(path, FileMode.Open);
using var accessor = mmf.CreateViewAccessor();
int value = accessor.ReadInt32(position: 1024);     // read directly from mapped memory
accessor.Write(2048, 42);
```

The OS pages data in on demand — you can work with files larger than RAM, and multiple processes can share a mapping. Use for huge read-mostly files (search indexes), zero-copy access, or inter-process shared memory. Niche but powerful.

## `System.IO.Pipelines` — high-perf streaming parse

For writing **high-throughput protocol parsers** (the engine behind Kestrel), `Pipelines` solves buffer management, partial-message handling, and back-pressure that are painful with raw `Stream`:

```csharp
PipeReader reader = PipeReader.Create(stream);
while (true) {
    ReadResult result = await reader.ReadAsync(ct);
    ReadOnlySequence<byte> buffer = result.Buffer;
    // parse complete messages out of `buffer`...
    reader.AdvanceTo(consumed, examined);   // tell the pipe what you used vs examined
    if (result.IsCompleted) break;
}
await reader.CompleteAsync();
```

It uses pooled buffers (near-zero allocation) and a multi-segment `ReadOnlySequence<byte>` so leftover bytes aren't copied. Full mechanics — `AdvanceTo(consumed, examined)`, `SequenceReader<byte>`, back-pressure thresholds — in CSharpBook Ch13 §03. Use it for network protocol parsing at scale, not for ordinary file reads (use `Stream`/`File` there).

## Common gotchas

### Blocking I/O on server threads

Synchronous `File.ReadAllText`/`stream.Read` on a request thread blocks a pool thread. Use async I/O in servers (CSharpBook Ch13 §01).

### Not looping on `Stream.Read`

A single `Read` may return fewer bytes than asked. Loop, or use `ReadExactly`/`CopyToAsync` (CSharpBook Ch13 §02).

### Hardcoded path separators

Breaks cross-platform. Always `Path.Combine`.

### Assuming case-insensitive filesystem

Linux is case-sensitive. Don't rely on `File.txt` matching `file.txt`.

### `MemoryStream`/disposal pitfalls

Forgetting to rewind (`Position = 0`) before reading back; `StreamReader` closing a stream you don't own (use `leaveOpen: true`). See CSharpBook Ch13 §02.

### Pipelines for simple file reads

Overkill — `Pipelines` is for high-scale protocol parsing. Use `Stream`/`File` for everyday I/O.

## Summary

- I/O is layered: **`Path`** (pure strings), **`File`/`Directory`** (filesystem), **`Stream`** (composable bytes), **`StreamReader/Writer`** (text+encoding), **`Pipelines`** (high-perf parse).
- Prefer **lazy** (`EnumerateFiles`, `ReadLinesAsync`) and **async** I/O on servers; respect **cross-platform** path/case/line-ending/permission differences.
- Streams **compose** (file → decrypt → decompress → text); honor the **`Read` contract** (may return fewer bytes; loop or use `CopyToAsync`).
- **`RandomAccess`** for thread-safe offset I/O; **memory-mapped files** for huge/shared files; **`Pipelines`** for high-throughput protocol parsing.
- Deep mechanics (atomic writes, `leaveOpen`, `AdvanceTo`, traversal safety): CSharpBook Chapter 13.
